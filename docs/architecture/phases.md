# Aervium Architecture: Phases

Part of the [Aervium architecture](../ARCHITECTURE.md).

## Phases

| Phase | Content | State |
|---|---|---|
| 0 Foundation and measurement | Project, adapter layer, telemetry (frame times, lows, MSPT, GC, RAM, VRAM, timing scopes), overlay, repeatable benchmark, unit tests | Done in 0.1 (unreleased) |
| 1 Core and stutter killers | Done: SPIR-V disk cache, persistent Vulkan pipeline cache, warm-up of built-in pipelines vanilla compiles mid-game, dynamic frame rate (background and pause), lighter chunk section locks, switchable modules, startup report. Moved to Phase 2: zero-allocation frame arenas (FFM) and job priorities, because chunk meshing is their first real user. Heap analysis on Can's PC (2026-10-15, render distance 32, Helion and Arkea, during the benchmark village scene after a full collection): 1469 MB live, 756 MB of it chunk data (block and biome containers, light arrays) that the client and the integrated server each keep; everything FerriteCore deduplicates on older versions (block state tables, neighbour tables, property maps, baked quads, model parts) adds up to 45 MB (3 %), because 26.3 already stores state neighbours in compact tables, so no memory module pays off now. Startup on the same PC: 25.6 s to the title screen; the main thread waits most of that time (42,000 park events in a JFR recording from the first second) while NeoForge scans and transforms classes, and the busiest CPU work is the Unicode font (about 1 s) and block shape caches, spread over threads; shader and pipeline caches already save the shader compiles. A ModernFix-like loader change is not in reach of a mod that loads after these steps | Done |
| 2 Streaming and meshing | Done: chunk builds on their own worker pool; compact terrain vertices (`compactVertices`, on by default: 5 % higher average, 1% low +3 %, 0.1% low +6 % and 20 to 32 % less video memory on Can's PC, 2026-10-15). Profile 2026-10-14: the mesh workers are 4 to 24 % busy and the render thread waits for them at most 17 ms per scene, so meshing does not limit frames yet; biome tint blending is 19 % of build time and the first target once it does. Measured again on 2026-10-15 (benchmark log, compact vertices on): chunk uploads take 0.04 to 0.19 ms per frame on average and 4.0 ms at most, the render thread waits for chunk builders at most 10.6 ms per 30 s scene and the 8 mesh workers are at most 21 % busy even in the elytra flight (883 builds per second); vanilla already builds the nearest section first and uploads through a staging buffer, and the light worker spends 15.6 to 62.5 ms CPU per 1200 parity ticks. Predictive streaming, budgeted uploads, job priorities, frame arenas and a faster light engine therefore have nothing to gain on this PC now; they come back when a profile shows the meshing, upload or light path in the frame time | Done |
| 3 Culling and draw | Done: software occlusion culling for the camera, Helion's shadow cascades, entities, block entities and particles. Done: optional leaf culling (off by default), face culling, culling results that survive slow frames and shadow results matched by section. Batched GUI and text drawing and multi-draw indirect need no module: in 26.3 vanilla sorts every GUI element by layer, pipeline and texture, merges them into one vertex buffer with one render pass and caches item icons in an atlas (`GuiRenderer`, `GuiItemAtlas`), and draws terrain with multi-draw indirect whenever the GPU supports it (`Minecraft.multiDrawIndirect`, on by default); Aervium's culling hooks both terrain paths | Done |
| 4 World and TPS | Done: point of interest search (`poiSearch`), entity collision search (`entityCollisions`) and idle hopper search (`hopperSearch`) skips, checked by the parity, worldgen and audit runs; parallel feature generation on dedicated servers (`parallelFeatures`, 23 to 27 % faster world generation; it cost frames in singleplayer); faster packet compression (`networkCompression`); flush batching is vanilla (`suspendFlushing`). Server profile on Can's PC (2026-10-15, dedicated server, 600 mobs on 289 force-loaded chunks of a normal world, JFR): mean tick 7.9 ms, longest 33.8 ms; block collisions 13 % of the server thread, mob brains 6 %, entity section lookups 5 %, chunk lookups for block reads 8 %, no single method above 8 %; with every scene of the benchmark at most 11.2 ms average MSPT, the tick stays far inside 50 ms and needs no further module now | Done |
| 5 Advanced Vulkan | Done: chunk draw lists without objects per draw or section (`directDraws`), a compact dirty section scan (`dirtySections`), late culling results widened without tests on the render thread, and two terrain draw paths chosen by the device feature `drawIndirectCount`: GPU-driven culling where it exists (`gpuCulling`), the CPU draw list elsewhere (see Terrain Draw Paths). Not built after measuring: meshlets and async queues. Tried and not kept: dropping shadow caster faces turned away from the sun (lesson L-102 of the workspace). Final comparison on Can's PC (2026-10-16, 1920x1009 window, render distance 32, two runs each, mean average / 1% low / 0.1% low): Aervium 326.2 / 129.9 / 71.3, Sodium 0.9.3 295.6 / 123.5 / 67.4, vanilla 218.2 / 64.6 / 42.5; with Helion, Aervium 143.4 / 64.8 / 40.5 against vanilla 111.7 / 39.0 / 24.8. Aervium trails Sodium only in the redstone scene (239 against 256 FPS). Follow-up the same day: `sectionGridMoves` and 1024 light snapshot shards for the slowest frames (1% low +6 %, elytra 1% low 115 to 126 to 132). The redstone and walk scenes are GPU bound (the render thread waits in `vkWaitSemaphores`); GPU timestamps per frame graph pass put the main pass at about 3.8 ms against 3.6 ms with Sodium in the redstone scene and every other pass level, so the gap is in drawing terrain on the GPU, not on the CPU. Tried and not kept: fog culling of sections the render distance fog hides completely (vanilla already keeps a circle; under 1 % difference) and a face bucket order with fewer draws (switching face culling off, one draw per layer, lost 5 % in those scenes, so draw count is not the limit) | Done |
| 6 Frame lock and LOD | In progress: distant terrain steps 1 and 2, with in-session client chunk capture, six-level LOD store, worker meshing, budgeted uploads, vanilla and Helion draw paths, extended far plane and fog, up to 512 chunks, seed generation of unvisited land in single player, distance presets, quality and CPU usage settings. Still planned: disk cache, reading saved chunks, dithered transitions, GPU tile culling, dedicated-server channel and dynamic resolution | In progress |
| 7 Beyond Sodium | Aggressive optimization without loss of picture quality: front-to-back order on the GPU-driven path, leaner terrain shaders, budgeted client light updates and chunk packets, GPU-driven Helion shadow cascades and translucent layer, crowded entity scenes (candidates and their weight in `docs/ROADMAP.md` of the workspace). Done on 2026-10-17: per-frame trace and GPU timings, the render thread owns chunk memory (`lockFreeSections`), mesh workers below normal priority, two spare swapchain images (`swapchainImages`), chunk packets decoded on workers (`chunkPacketDecoding`); 0.1% low 118 to 207 FPS at render distance 12. The other candidates were measured and not built (draw order on the GPU path, Hi-Z, GPU-driven shadow cascades; reasons in `plans/aervium-phase-7-plan.md` of the workspace) | Done |
