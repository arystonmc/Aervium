# Kinetic Architecture: Vanilla Parity Check

Part of the [Kinetic architecture](../ARCHITECTURE.md).

## Vanilla Parity Check

`./gradlew runParity` starts a dedicated server in `runs/parity` with a fresh flat world, runs a fixed scenario and stops; `-PparityModules=off` writes every module as off before the run and `-PparityOff=a,b` turns off only the named modules.

1. Seed 1095062134, flat grass world, no structures, time, weather and mob spawning frozen, the server never pauses when empty.
2. After 40 ticks the level random and the random tick position generator get fixed seeds and `ParityScenario` builds an observer clock with a sticky piston, a hopper chain between chests, a burning furnace, a wheat farm, water and lava, saplings, sugar cane and torches in 16 force-loaded chunks.
3. Every tick a fixed sequence places light sources and blockers (glowstone, sea lanterns, stone, glass, slabs, stairs, leaves, tinted glass, air) in a 40 x 8 x 8 light lab, 4 per tick or `kinetic.parity.lightChanges`, so block and sky light keep changing.
4. After every tick the harness waits until the light worker has finished every queued task for the scenario chunks. Vanilla lights on a worker thread, so without this a random tick that reads light (grass dying under a new block) would depend on thread timing.
5. Every 200 ticks for 1200 ticks the log prints three hashes of the 48 x 48 x 21 area: blocks (state, block entity data, scheduled ticks), light (block and sky light) and entities.

Two runs with the same settings must print the same hashes, and a run with every module off must print the same hashes as a run with every module on. Any optimization that touches world logic has to keep this true; a different hash shows the first checkpoint where the world diverged.

`-Dkinetic.parity.worldgen=true` with `-PparityWorld=normal` runs the worldgen check instead: ticks are frozen, 25 x 25 chunks (`kinetic.parity.worldgenRadius`, 12) generate on the fixed seed, and `ChunkStatusTasksTerrainMixin` hashes every chunk right after its terrain step (noise, surface, carvers, biomes). The log prints one terrain hash, a save and load round trip of every section (mismatches must be 0), the generation time and the process CPU time. Features are left out on purpose: vanilla places overlapping features of neighbouring chunks in thread order, so two plain vanilla runs already differ there. CI runs this check with modules on and off as well.

`-Dkinetic.parity.mobs=N` with `-PparityWorld=normal` and a force radius spawns N cows, sheep, pigs, chickens and villagers on dry land over the force-loaded square and logs the mean and longest server tick, wall and server thread CPU; this is the server load benchmark (hashes are not comparable then). Cloud profile with 600 mobs on 289 chunks after `poiSearch`: mob movement and collisions about 15 %, villager brains about 21 %, entity lookups about 9 %. Two ideas were measured and not kept: skipping air before the block shape lookups in collisions, and flattening the brain's behavior maps into arrays; neither moved CPU per tick beyond run-to-run noise. `-Dkinetic.poiAudit=true` runs the vanilla point of interest search next to the indexed one for every column and logs the number of searches, records and mismatches; `-Dkinetic.collisionAudit=true` runs the vanilla entity search for every entity collision query the section counts skip and counts the ones where vanilla found an entity. `-Dkinetic.parity.hoppers=N` places N idle hoppers on dry land (with `-Dkinetic.hopperAudit=true` one in 64 also gets a full chest minecart on top and one in 64 a dropped item stack); `-Dkinetic.hopperAudit=true` keeps the vanilla hopper entity searches, counts the ones the section counts would skip and the ones among them where vanilla found an entity. CI runs the three audits with 300 mobs and 500 hoppers and requires 0 mismatches. Measured with dense minecarts next to most hoppers, `hopperSearch` skips few container searches and gives no gain; with plain idle hoppers it cuts server tick CPU by about 11 %.

The same run doubles as a light benchmark: the log prints the wall and CPU time the server light worker spent before the scenario and during it. `-Dkinetic.parity.lightChanges=400` makes block light heavy; `-PparityWorld=normal` with `-Dkinetic.parity.forceRadius=12` generates 625 chunks of normal terrain first (hashes are not comparable then, normal worlds have mobs). Cloud results on 4 cores: light was about 5 % of the chunk generation CPU (noise filling 57 %, surface 21 %, features 17 %), and 400 block changes per tick cost about 17 µs each. Bigger chunk and section caches inside the light engine changed neither number beyond noise, so they were not kept.
