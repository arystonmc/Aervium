# Distant Terrain Review (historical): Research and Plan

Historical record, kept unchanged: the distant terrain review of 2026-10-19 and its follow-up of 2026-10-20. Part of the [Kinetic architecture](../ARCHITECTURE.md); the current design is in [the distant terrain section](engine-systems--terrain-and-join.md).


Research date: 2026-10-19. Follow-up implementation: 2026-10-20. Scope: the local Voxy 0.2.19 beta and Distant Horizons 3.3.4 for 26.3 binaries, and Kinetic's current Phase 6 working tree. This is an inspection of those versions, not a claim about later releases. No game or comparative benchmark was run for this review.

## Voxy

Paths in this section are under `me/cortex/voxy/` unless an asset path is given.

| Area | Observed behavior and evidence |
|---|---|
| Unvisited seed terrain | No built-in distant seed generation was found in this binary. `commonImpl/importers/WorldImporter.java` reads existing chunks; `commonImpl/mixin/chunky/MixinFabricWorld.java` captures chunks produced by an external pregenerator. `commonImpl/WorldIdentifier.java` uses world identity/seed for cache separation, which is not terrain generation. Therefore there are no independent noise, surface or feature generation stages or generated chunk saves to attribute to Voxy itself. |
| Visited data | `common/world/service/VoxelIngestService.java` queues chunk sections and copies their sky/block light layers for service processing; `common/voxelization/WorldConversionFactory.java` converts block states, biomes and light; `common/world/WorldUpdater.java` propagates the hierarchy. This retains real blocks including trees and overhangs. |
| Existing region files | `commonImpl/importers/WorldImporter.java` scans region headers and chunk stream compression, decodes NBT section palettes and light, and submits voxel conversion without loading game chunks or creating chunk tickets. It also imports zipped region directories. In this version external chunk streams are rejected. Imports are asynchronous and wait when the outstanding chunk count exceeds 10,000. |
| Representation | `common/world/WorldSection.java` holds 32 cubed cells in a 32,768-element `long[]`, with X contiguous, then Z, then Y: 256 KiB for the cell array before overhead. `common/world/other/Mapper.java` packs a block-state mapping ID (20 bits), biome mapping ID (9 bits) and sky/block light (8 bits) into each cell. This is a volume, not one height per column. `common/voxelization/WorldVoxilizedSectionMipper.java` builds coarser voxels. Full vertical geometry is possible, at a much larger cost than Kinetic's heightfield. |
| Persistence/compression | `common/world/SaveLoadSystem3.java` serializes a section key, metadata, 32,768 short palette indices and a long-valued palette; mapped block/biome identities are stored separately. `common/StorageConfigUtil.java` selects a section serializer over a compression adapter over RocksDB by default, with Zstandard level 1. `common/config/storage/` also contains LMDB, memory and other optional backends; `common/config/compressors/` includes LZ4. `common/world/ActiveSectionTracker.java` manages residency rather than retaining every decoded section forever. |
| LOD selection and culling | `client/core/rendering/hierachical/NodeManager.java`, `AsyncNodeManager.java` and `assets/voxy/shaders/lod/hierarchical/traversal_dev.comp` maintain/traverse a spatial hierarchy, using projected size and subdivision settings. `assets/voxy/shaders/lod/frustum.glsl`, `assets/voxy/shaders/hiz/hiz.comp` and the `lod/gl46/cull/` shaders support GPU visibility/depth culling. This is much more than Kinetic's horizontal distance test. |
| Transitions | The hierarchy coordinates parent/child availability. `client/core/rendering/building/RenderDataFactory.java` obtains neighboring section faces and creates boundary geometry; this is volumetric neighbor meshing, not Kinetic's fixed heightfield skirt. `client/core/NormalRenderPipeline.java` and `assets/voxy/shaders/post/blit_texture_depth_cutout.frag` composite distant color/depth against real terrain, with selectable fog/fade. A universal claim of morphing or a particular dithering algorithm is not justified by those paths alone. |
| Meshing and vertices | `RenderDataFactory.java` and `client/core/util/ScanMesher2D.java` merge compatible faces into rectangles. Each resulting quad occupies one packed 64-bit record; `assets/voxy/shaders/lod/quad_format.glsl` and `lod/gl46/quads3.vert` decode it and reconstruct corners. This is 8 bytes per quad record, not 8 bytes per conventional vertex. Model data lives separately. |
| GPU storage/draws/uploads | `client/core/rendering/section/geometry/BasicSectionGeometryManager.java` places sections in a shared geometry allocation with section metadata, rather than one GPU object per tile. `client/core/rendering/section/backend/mdic/MDICSectionRenderer.java` and `lod/gl46/cmdgen.comp` implement indirect rendering. `AsyncNodeManager.java` limits a geometry-update batch by count, available geometry space and approximately 1,024,000 estimated upload bytes. These are implementation budgets, not a time guarantee. |
| Lighting, water and color | `client/core/model/` prepares model/material information; `lod/block_model.glsl` and `lod/lighting.glsl` reconstruct appearance using block identity, biome and light. The renderer has distinct translucent handling (`lod/gl46/buildtranslucents.comp`), fog/fade composition and optional screen-space ambient occlusion (`client/core/SSAO.java`). Water retains a fluid/material identity instead of becoming an opaque blue heightfield. |
| Actual controls | `client/config/VoxyConfig.java`: enabled/rendering/ingestion are distinct switches; `sectionRenderDistance` changes coverage in units of 512 blocks (default 16 means 8,192 blocks); `subDivisionSize` changes the projected subdivision threshold, hence geometry/residency; `serviceThreads` changes shared service concurrency; `dontUseSodiumBuilderThreads` changes builder scheduling; fog mode chooses fog/fade combinations; SSAO mode controls the additional screen-space pass. `client/core/rendering/hierachical/HierarchicalOcclusionTraverser.java` squares the subdivision size for its area threshold; `client/core/VoxyRenderSystem.java` can adjust it under geometry pressure. `common/thread/UnifiedServiceThreadPool.java` schedules services. Minimum priority alone is not a CPU duty-cycle cap, and no DH-style duty-cycle setting is exposed here. |

## Distant Horizons

Paths in this section are under `com/seibel/distanthorizons/` unless otherwise stated.

| Area | Observed behavior and evidence |
|---|---|
| Unvisited seed terrain | `core/generation/DhWorldGenerator.java`, `core/generation/queues/WorldGenerationQueue.java`, `common/wrappers/worldGeneration/DhChunkGenerator.java` and its `step/` directory coordinate isolated proto-chunk batches with neighbor margins. Available stages include structure starts/references, biomes, 26.3 terrain and features; `step/StepTerrain.java` calls vanilla `buildTerrain`, and `step/StepFeatures.java` runs decoration. Consequently actual seeded trees require the feature stage, not a biome canopy offset. `DhLightingEngine.java` supplies distant lighting. |
| Generation modes/save behavior | `api/enums/worldGeneration/EDhApiGeneratorPlan.java` exposes surface then chunks, surface only, chunks only and disabled. `DhRoughSurfaceGenerator.java` evaluates density and approximate surfaces for early coverage. Ordinary distant batches create transient proto chunks and feed LOD storage, without enrolling them as normal full chunks. The separate `DhInternalServerGenerator.java` explicitly tickets full chunks through the server executor and later releases them; that mode has normal server generation/save implications. They must not be conflated. |
| Threading/throttle | Generation runs through dedicated executors, with per-thread generation parameters in `common/wrappers/worldGeneration/params/ThreadWorldGenParams.java`. `core/util/threading/ThreadPoolUtil.java` configures pools; `RateLimitedThreadPoolExecutor.java` idles after tasks according to the run-time ratio. Counts and the ratio both affect CPU use. The internal-server mode necessarily schedules some work on the server executor. |
| Visited/saved capture | `core/api/internal/chunkUpdating/WorldChunkUpdateManager.java` and `core/api/internal/chunkUpdating/ChunkUpdateQueueManager.java` coordinate chunk updates and asynchronous conversion. `common/wrappers/chunk/ChunkWrapper.java` exposes section blocks, biome and light; `core/dataObjects/fullData/sources/FullDataSourceV2.java` builds vertical runs from them. |
| Reading disk without chunk loads | `common/wrappers/worldGeneration/chunkFileHandling/ChunkFileReader.java` reads chunk NBT using the region cache or the existing I/O worker. `mimicObject/RegionFileStorageExternalCache.java` manages region access, and `chunkFileHandling/ChunkCompoundTagParser.java` reconstructs transient section palettes/light. This bypasses full chunk loading; absence can produce an empty proto chunk for subsequent isolated generation. |
| Full data layout | `core/util/FullDataPointUtil.java` uses a 64-bit vertical run: a mapping ID field (32 allocated bits), height and relative minimum Y (12 bits each), sky and block light (4 bits each). `core/dataObjects/fullData/FullDataPointIdMap.java` maps identities to block state plus biome. `FullDataSourceV2.java` stores a 64 by 64 grid of variable-length long lists, plus column generation/compression metadata and adjacent data. It can represent caves, overhangs and floating layers. Cost scales with vertical/material transitions rather than with world height alone. |
| Render data and persistence | `core/util/RenderDataPointUtil.java` packs resolved RGB, reduced alpha, vertical bounds, both lights and a material category into another 64-bit representation. `core/sql/dto/FullDataSourceV2DTO.java` serializes compressed column data, mapping, generation steps, compression mode and adjacent data. `sqlScripts/0020-sqlite-createFullDataSourceV2Tables.sql` and `0090-sqlite-addAdjacentFullDataColumns.sql` define the SQLite cache. `api/enums/config/EDhApiDataCompressionMode.java` includes uncompressed, LZ4, Zstandard block/stream and LZMA2. These codecs are distinct from geometric world-data simplification. |
| Selection/transitions/culling | `core/render/QuadTree/LodQuadTree.java` chooses horizontal quadtree detail and waits for GPU upload completion when changing coverage. `core/render/RenderBufferHandler.java` performs CPU frustum culling, with override hooks for camera/shadow frusta. `core/dataObjects/transformers/FullDataOcclusionCuller.java` removes hidden full-data content before rendering; it is not evidence of a Voxy-like GPU-driven hierarchy/Hi-Z path. Neighbor render data is considered when constructing side faces. `assets/distanthorizons/shaders/terrain/blaze/frag.fsh` optionally dithers near LOD clipping; `shaders/fade/blaze/vanilla_fade.fsh` and `dh_fade.fsh` blend the real and distant color/depth results over distance ranges. The OpenGL equivalents are under `shaders/fade/gl/`. These are separate from parent/child readiness and are not a general guarantee of artifact-free transitions. |
| Mesh/buffer layout | `core/dataObjects/render/bufferBuilding/LodQuadBuilder.java` premerges and sorts compatible quads for further merges. It writes 16-byte conventional vertices containing short positions, color/light/material metadata and texture information; four vertices cost 64 bytes per quad before indices. `ColumnRenderBufferBuilder.java` builds section data; `core/dataObjects/render/bufferBuilding/LodBufferContainer.java` owns separate opaque/transparent section buffers. `common/render/blaze/BlazeDhTerrainRenderer.java` submits individual indexed buffer draws. This is section-based buffering, not Voxy's single packed-quad heap. `core/render/RenderThreadTaskHandler.java` budgets render/upload tasks against roughly half the configured frame interval, using elapsed time and the previous task's cost to decide whether to continue. |
| Lighting/fog/water/tint | Block/biome identities survive in full data and are resolved during `core/dataObjects/transformers/FullDataToRenderDataTransformer.java`. `common/render/blaze/BlazeDhTerrainRenderer.java` binds the game lightmap and block atlas, uses opaque/transparent pipelines and understands forward/reversed depth. This binary has native RenderPearl support as well as OpenGL: `common/wrappers/DependencySetup.java` chooses the renderer definition. `core/render/renderer/FogRenderParamFactory.java` builds far/height fog controls; color source, start/end, density/falloff and height mixing are configurable. Transparency, ambient occlusion, tint/brightness/saturation and textures add quality and GPU work beyond Kinetic's opaque RGB surfaces. |

Actual quality and CPU controls (`core/config/Config.java`, `core/config/eventHandlers/presets/RenderQualityPresetConfigEventHandler.java`, `ThreadPresetConfigEventHandler.java`):

- Horizontal quality moves detail drop distances; maximum horizontal resolution sets the finest cell width. Vertical quality limits retained render layers. These affect geometry and memory, rather than generation thread count.
- Distance sets area coverage. Transparency, textures, ambient occlusion, fog and noise settings affect render appearance and passes. Brightness/saturation alter resolved color, not the seed.
- World compression chooses strict block changes versus visually equivalent changes (including ignoring hidden interior changes). File compression chooses a storage codec. Neither is the horizontal quality setting.
- Thread presets select roughly 10%, 25%, 50%, 75% or 100% of available processors; minimal impact also uses a 0.5 run-time ratio. Custom count and run-time ratio permit independent concurrency and duty-cycle control.
- Generation plan and target stage determine whether the rough surface, real terrain, decoration or full server generation runs. Pre-existing-only behavior cannot create trees in an unsaved chunk.

The quality presets concretely combine those controls: Minimum uses two-block horizontal resolution, one vertical layer, no transparency/SSAO/anti-aliasing/fade; Low uses block resolution, Low vertical/horizontal quality, no transparency/SSAO and single-pass real-terrain fade; Medium and higher enable transparency, SSAO and double-pass fade with increasing horizontal/vertical detail. Low and higher enable anti-aliasing and LOD dithering. Biome blending increases from zero to one to three; the high presets disable cave culling. `api/enums/config/EDhApiVerticalQuality.java` gives the finest-level layer budgets as 1 (height map), 4 (Low), 6 (Medium), 16 (High), 32 (Very High), 64 (Extreme) and 512 (Pixel Art), decreasing at distance. These are render-layer budgets, not a promise to retain every full-data run in the mesh.

## Kinetic gap analysis

The baseline paths are `src/main/java/com/aryston/kinetic/core/lod/`, `client/lod/`, the three distant-terrain mixins, `client/config/`, `config/KineticConfig.java` and `src/main/resources/assets/kinetic/shaders/lod/`.

| Topic | Baseline and implication |
|---|---|
| Strength: bounded representation | A 64 by 64 `LodTile` has 32 KiB of packed samples, versus 256 KiB for one decoded Voxy 32-cube voxel array. Coverage and represented geometry differ, so this is not an equal-quality memory benchmark. The fixed one-surface format is inherently cheap. |
| Strength: integration | Native 26.3 RenderPearl/Vulkan draws and an optional Helion geometry-buffer hook share normal frame ownership. Kinetic needs no separate renderer dependency. This is an integration advantage over Voxy's renderer-specific path, not an exclusive capability over DH, whose inspected binary also supports RenderPearl. |
| Strength: seed preview | Sparse `getBaseHeight` plus biome colors provides independent coarse coverage without creating/saving chunks. It is useful before exact data arrives, and Voxy itself has no equivalent seed generator in the inspected binary. |
| Missing real generation | `GeneratedColumns` interpolates ocean-floor height and applies categorical biome color plus a uniform five-block forest lift. It does not run terrain surface rules, structures or features. Trees and real materials cannot be recovered from that approximation. |
| Missing sources/cache | Only current-session client chunks are captured. Saved worlds are ignored and there is no persistent LOD cache. Repeated visits/games redo work and lose player builds outside the view. |
| Representation/appearance | One RGB surface cannot represent overhangs, layered foliage, cliff material changes or light values. `ColumnSampler` uses tint directly or map color, not texture-average albedo. Water is opaque and the forward shader is effectively fullbright. Helion receives full sky light and a derived normal, but side shading is already baked into RGB. |
| Coverage bugs | A populated tile is not necessarily complete. Sparse child data can overwrite a broader seed cell, and a partially populated child can trigger a split. Provenance and footprint completeness must be distinct. |
| Work/residency | A count of six uploads does not bound bytes/time. The ready queue and store can grow; old generation can occupy workers after a world change; failed requests can remain permanently suppressed. Priority is not CPU throttling. |
| Mesh/draw cost | Every present cell emits a top quad, even across a flat uniform lake; every tile has its own draw/buffer. Fixed edge skirts do not adapt to larger inter-level height differences. No LOD-specific frustum or GPU occlusion path exists. |
| Transitions | Parent/child availability is only partially coordinated; real terrain is clipped by a render-distance square rather than actual uploaded chunk coverage. Skirts hide some cracks but there is no geometric morph or temporal coverage fade. |

## Ranked implementation plan

The order favors independently testable correctness and bounded work before increasing source fidelity. Expected impacts are hypotheses, except for exact byte/quad counts in unit fixtures. Matching both references while beating both on all resources remains a target, not a demonstrated result.

| Rank | Change | Expected visual effect | Expected resource effect |
|---|---|---|---|
| 1 | Preserve provenance and complete footprints; hold coarse coverage until children are complete and uploaded | Prevent sparse replacements and early splits from cutting holes in the horizon | Small flag/counter cost; no larger sample |
| 2 | Merge equal top rectangles and wall runs; bound ready meshes and per-frame upload bytes/time | Identical retained surfaces; faster convergence without upload bursts | Large vertex reduction on flat areas; bounded backlog; uneven terrain gains less |
| 3 | Read saved chunk section palettes through vanilla asynchronous storage, resolve their real top blocks/biomes, prefer these over the seed preview | Actual saved trees, builds and surface materials beyond the current view in single player | More bounded background I/O/decoding; avoid server chunk tickets and generation; retain the cheap far preview |
| 4 | Cancel stale generation within tiles, recover failed requests, throttle Low/Balanced and bound sample residency | Fewer stale replacements and missing tiles after setting/world changes | Less wasted CPU, controlled duty cycle and memory; deliberately slower fill on Low |
| 5 | Neighbor-aware edge skirts and changed-border remeshing | Hide cracks larger than the fixed skirt at mixed detail boundaries | Small boundary work on the store worker; no extra vertex format |
| 6 | Isolated original 26.3 terrain/feature generation with dependency neighborhoods and a persistent versioned cache | Real seeded surface blocks, structures and trees in never-saved land | Significant CPU initially; amortize via cache, coarse preview and near-first exact refinement |
| 7 | Optional capped vertical spans near the transition; retain cheap single surfaces far away | Cheap overhangs, separated canopy/ground and cliff materials | Extra bytes only where needed; must measure span limits against quality |
| 8 | Texture-average albedo, retained light, water/material separation and forward lightmap shading | Match resource packs/day-night/water; avoid tint-only colors and baked Helion shading | Small material tables, new packed attributes and transparency cost |
| 9 | Actual real-chunk coverage mask, complementary stable transitions and geometric detail morphing | Remove clip-square holes and reduce visible popping | Requires mesh-ready chunk hooks and both draw paths; coordinate depth/shadows carefully |
| 10 | Conservative frustum bounds, pooled geometry and indirect LOD draws, then measured occlusion | Same picture with fewer submissions/invisible triangles | Lower CPU/GPU submission cost; more allocator/synchronization complexity |
